# Research: Etebase server + etesync-dav on NixOS

Ticket: `.scratch/optiplex-nixos-migration/issues/09-research-etesync.md` (Optiplex → NixOS map).
Researched 2026-11-06 against NixOS/nixpkgs `master` (identical files on `nixos-unstable`), upstream `etesync/server` and `etesync/etesync-dav`, and read-only inspection of the live Optiplex.

## Question

Can the Etebase server (today a Python venv in `/srv/etesync/etebase`, uvicorn on :25567, behind `etesync.nnik.dev`) and etesync-dav (`/srv/etesync-dav`, behind `dav.nnik.dev` on :37358) run from nixpkgs (`services.etebase-server`, `etesync-dav` package)? Which database does the existing server use (sqlite or Postgres `djangodb`?), and how is its State migrated?

## Short answer

- **Yes, both run from nixpkgs, each with its own NixOS module**: `services.etebase-server` [1] and `services.etesync-dav` [2] (a module exists, not just the package). Both have NixOS VM tests that pass on Hydra [3][4][5][6].
- **Versions line up**: nixpkgs ships etebase-server **0.14.2** [7]; the Optiplex runs `v0.14.2-2-g6ac5412` (two commits later, last upstream commit 2024-07-12, "Bump django version") [8]. etesync-dav: nixpkgs **0.35.1** [9], Optiplex runs the 0.34.0 standalone binary, upstream just released 0.36.0 [10].
- **The live server uses SQLite**, not Postgres: `[database] engine = django.db.backends.sqlite3`, `name = db.sqlite3` (2.6 MB, 3 users, 37 `django_etebase` migrations applied). No `djangodb` Postgres DB is in use by Etebase.
- **Etebase State** = the SQLite DB + `media_root` (`/srv/etesync/media`, 11 MB, `user_N/` dirs) + `secret.txt` (Django `SECRET_KEY`; backing it up is optional per upstream) [11]. `static/` is regenerated by the module's `collectstatic` [1].
- **Migration path (SQLite kept)**: copy `db.sqlite3` → `/var/lib/etebase-server/db.sqlite3`, media → `/var/lib/etebase-server/media` (or set `media_root`), chown to `etebase-server`; the module's preStart runs `migrate` + `collectstatic` on first start [1].
- **Migration path (shared Postgres)**: the module's `database.engine` enum allows `django.db.backends.postgresql` and the package includes psycopg2 by default [1][7]; data would move via Django `dumpdata`/`loaddata` (or pgloader). Ordering after `postgresql.service` must be added by hand [1].
- **etesync-dav State** = `/root/.local/share/etesync-dav/{etesync_creds,htpaswd,etebase_data.db}` (2.9 MB, one user). Module data dir is `/var/lib/etesync-dav` with `DynamicUser` [2]. `etesync_creds` holds an **unencrypted** saved Etebase session (`etebase.save(None)`) [12] and must be treated as a secret.
- **Coupling gotcha**: the stored etesync-dav user has `serverUrl = http://localhost:25567`, so the new Etebase must still answer there (set `port = 25567`, keep `localhost` in `allowed_hosts`), or the URL in `etesync_creds` must be edited/re-added [12].
- **Caddy gotchas**: Etebase needs the real `Host` (Caddy forwards it by default) [11][13]; the etesync-dav admin UI (`/.web`) only accepts `Host: localhost` under Flask ≥ 3.1 (`TRUSTED_HOSTS`) [14][15], which nginx satisfies today by accident (`Host $proxy_host`) [16] but Caddy won't without `header_up Host`.

## Details

### Current setup on the Optiplex (read-only inspection, 2026-11-06)

- `etesync.service`: user `etesync`, `WorkingDirectory=/srv/etesync/etebase`, `ExecStart=/srv/etesync/etebase/.venv/bin/uvicorn etebase_server.asgi:application --host localhost --port 25567`. Python 3.12.13, Django 4.2.14, FastAPI 0.111.0, uvicorn 0.30.1. Git checkout at `6ac5412` (`v0.14.2-2-g6ac5412`).
- `/srv/etesync/etebase/etebase-server.ini`:
  - `[global] secret_file = secret.txt` (relative → `/srv/etesync/etebase/secret.txt`, 50 bytes), `debug = false`, `static_root = /srv/etesync/static`, `media_root = /srv/etesync/media`.
  - `[allowed_hosts] allowed_host1 = localhost`, `allowed_host2 = etesync.nnik.dev`.
  - `[database] engine = django.db.backends.sqlite3`, `name = db.sqlite3` (→ `/srv/etesync/etebase/db.sqlite3`, 2.6 MB). Empty `[database-options]`, no LDAP, no redis.
  - DB contents: 3 rows in `myauth_user`; latest migrations `django_etebase 0037_auto_20210127_1237`, `myauth 0003`, `token_auth 0001`.
- `/srv/etesync/media`: 11 MB, per-user dirs `user_1/`, `user_4/`, … (encrypted chunks). `/srv/etesync/static`: 1.9 MB (regenerable).
- `etesync-caldav.service`: `ExecStart=/srv/etesync-dav/etesync-dav` (PyInstaller binary, "EteSync DAV version: 0.34.0, Radicale version: 3.2.0"), **no `User=` → runs as root**, no environment → defaults: listens on `localhost:37358` (v4 + v6), data dir resolved via appdirs to `/root/.local/share/etesync-dav` [17].
- `/root/.local/share/etesync-dav/`: `etesync_creds` (681 B, JSON, one user, keys `serverUrl` + `storedSession`; `serverUrl = http://localhost:25567`), `htpaswd` (22 B, the generated DAV password), `etebase_data.db` (3 MB SQLite cache: tables `user, collectionentity, config, itementity, hrefmapper`).
- nginx: `etesync.nnik.dev` → `proxy_pass http://localhost:25567` with `Host $host`, websocket upgrade headers, plus `location /static/ { alias /srv/etesync/static/; }`. `dav.nnik.dev` → `proxy_pass http://localhost:37358` with no header overrides. The dav vhost is getting internet scanner traffic (journal shows 401s for `/api/mcp`, `/sse`).

### Etebase server in nixpkgs

- Package `etebase-server` 0.14.2 from tag `v0.14.2`, `withPostgres ? true` (adds `psycopg2`), `withLdap ? false`; includes `uvicorn`, `websockets`, `uvloop`, `httptools`, `redis` [7]. A nixpkgs patch removes the default `secret.txt` path so `secret_file` must be configured [18].
- nixpkgs builds it against `python3.pkgs.django`, which is Django 5 (`django = self.django_5`) [19], while upstream pins `django>=4.0,<5.0` [20]. The package and its VM test (which runs `etebase-server test` and `check`) are green on Hydra (package build 2026-10-22, test 2026-11-01) [3][5], so this works in practice, but it is a divergence from upstream's pin. The two upstream commits after 0.14.2 that the Optiplex runs are a Django bump and a null-collection-type fix [8]; they are not in nixpkgs.
- Module `services.etebase-server` [1]:
  - Options: `enable`, `package`, `dataDir` (default `/var/lib/etebase-server`), `port` (default 8001), `unixSocket`, `openFirewall`, `user` (default `etebase-server`, created as system user), and freeform INI `settings`.
  - `settings.global.secret_file` (default `null` — must be set), `static_root`/`media_root` (default `${dataDir}/static|media`), `settings.allowed_hosts.allowed_host1` (default `"0.0.0.0"` — must be overridden), `settings.database.engine` (enum: sqlite3 or postgresql, default sqlite3), `settings.database.name` (default `${dataDir}/db.sqlite3`). Being freeform, other keys (`database.user`, `database.host`, `[database-options]`) pass straight into the INI, which upstream maps to Django `DATABASES` (`{x.upper(): y}`) and `OPTIONS` [21].
  - Service: `User = cfg.user`, `WorkingDirectory = dataDir`, `Restart = always`, `after = network.target systemd-tmpfiles-setup.service` only (no Postgres ordering). preStart runs `etebase-server migrate --no-input` and `collectstatic --no-input --clear` whenever the package store path changes (tracked in `${dataDir}/src-version`). Runs `uvicorn --host 0.0.0.0 --port <port>` or `--uds <unixSocket>`.
  - Note: with a TCP port it binds **0.0.0.0**, not localhost; only the firewall (`openFirewall = false` default) keeps it off the LAN.
  - Puts a wrapped `etebase-server` (manage.py) on `PATH` with the generated INI for admin commands like `createsuperuser`.
- Static files: Etebase's FastAPI app mounts `STATIC_URL` from `STATIC_ROOT` itself [22], so Caddy does not need a separate `/static/` file server (nginx's alias today is optional).
- Reverse proxy: upstream says the server must see the original `Host` header [11]. Caddy passes `Host` through unchanged by default [13]; websockets are proxied by Caddy's `reverse_proxy` without extra config [13].

### etesync-dav in nixpkgs

- Package `etesync-dav` 0.35.1 with a Radicale 3.6 compat patch (upstream PR #365), `pythonRelaxDeps = [ "radicale" ]` [9]. Upstream 0.36.0 (2026-11-02) fixes Radicale ≥ 3.5.x compatibility and a high-CPU select() loop [10]; nixpkgs hasn't picked it up yet.
- Module `services.etesync-dav` [2]: options `enable`, `host` (default `localhost`), `port` (default 37358), `apiUrl` (default `https://api.etebase.com/partner/etesync/`), `openFirewall`, `sslCertificate`/`sslCertificateKey`. Service sets `ETESYNC_LISTEN_ADDRESS`, `ETESYNC_LISTEN_PORT`, `ETESYNC_URL = apiUrl`, `ETESYNC_DATA_DIR = /var/lib/etesync-dav`; `DynamicUser = true`, `StateDirectory = etesync-dav`, `Restart = on-failure`, `RestartSec = 30min 1s`.
  - With `DynamicUser`, the real directory is `/var/lib/private/etesync-dav` (symlinked from `/var/lib/etesync-dav`), and systemd recursively fixes ownership of a pre-existing `StateDirectory` on start [23] — so restored files can be copied in as root.
  - `apiUrl` is only the default for users **added** via the web UI (empty "Server URL" field) [24]; existing users keep their stored `serverUrl` [12]. Setting `apiUrl` to the self-hosted server makes future re-adds point at the right place.
  - `RestartSec = 30min` means a crash leaves DAV down for half an hour; can be overridden with `systemd.services.etesync-dav.serviceConfig.RestartSec`.
- Data files (upstream config): `ETESYNC_DATA_DIR` (default appdirs `user_data_dir`), `etesync_creds`, `htpaswd`, `etebase_data.db`, optional `etesync.crt/.key` [17]. `etesync_creds` stores `storedSession = etebase.save(None)` (no encryption key) and `serverUrl` [12][24]. `htpaswd` holds the DAV password the clients (Thunderbird etc.) use [24]; keeping it avoids reconfiguring clients. `etebase_data.db` is a local cache that can be rebuilt by re-syncing.
- Web UI host check: the admin UI is a Flask app served under `/.web` through a Radicale web plugin [25], with `app.config["TRUSTED_HOSTS"] = LISTEN_ADDRESS` [14]. Flask 3.1 started enforcing `TRUSTED_HOSTS` during routing [15] (nixpkgs ships Flask 3.1.3 [26]); Werkzeug compares the hostname against the list [27]. Today nginx sends `Host: localhost:37358` because nginx's default is `proxy_set_header Host $proxy_host` [16]. Caddy forwards the original `Host: dav.nnik.dev` [13], so `/.web` would likely be refused unless Caddy sets `header_up Host {upstream_hostport}` (or `localhost`). CalDAV/CardDAV paths are Radicale, not Flask, and should be unaffected — to be confirmed in the VM test.

### State migration steps (either DB option)

1. Stop `etesync` and `etesync-caldav` on Arch; copy `/srv/etesync/etebase/db.sqlite3`, `/srv/etesync/etebase/secret.txt`, `/srv/etesync/media/`, and `/root/.local/share/etesync-dav/{etesync_creds,htpaswd,etebase_data.db}`. Upstream lists DB + `MEDIA_ROOT` as what needs backing up [11].
2. `secret.txt` → sops-nix secret owned by `etebase-server`, referenced via `services.etebase-server.settings.global.secret_file` (required by the nixpkgs patch [18]). Losing it is not fatal (upstream: revocable, "not essential") [11], it only invalidates Django sessions/signatures.
3. Media → `${dataDir}/media` (or point `media_root` at another path, e.g. on the Data disk), `chown -R etebase-server:etebase-server`.
4. DB: see options below. On first start the module runs `migrate` (no-op or Django 5 related migrations) and `collectstatic` [1].
5. etesync-dav files → `/var/lib/private/etesync-dav/` (systemd chowns on start [23]); keep `serverUrl` reachable (see coupling note).
6. Verify: `etebase-server check` (wrapper on PATH [1]), log in from the EteSync app, Thunderbird DAV sync with the existing DAV password.

## Options / trade-offs

### A. Database

| Option | What it takes | Pros | Cons |
|---|---|---|---|
| **A1. Keep SQLite** (module default) | Copy `db.sqlite3` to `${dataDir}`; no DB settings needed [1] | Zero conversion risk; identical to today; the nixpkgs VM test exercises exactly this path [5] | Diverges from the map's "one shared PostgreSQL" standing decision; Backup has to snapshot a live SQLite file safely (e.g. `sqlite3 .backup` or stop the service) |
| **A2. Shared PostgreSQL** | `settings.database = { engine = "django.db.backends.postgresql"; name = "etebase-server"; user = "etebase-server"; host = "/run/postgresql"; }` + `ensureDatabases/ensureUsers` + `systemd.services.etebase-server.{after,requires}` on Postgres [1][21][28]. Data: on the old box `manage.py dumpdata --natural-foreign --natural-primary -e contenttypes -e auth.Permission` → `loaddata` on a freshly migrated Postgres DB [29]; Django's `loaddata` resets Postgres sequences afterwards [30]. Alternatively pgloader's SQLite source [31] | Matches the standing decision; one backup mechanism (pg_dump) for all services; peer auth over the socket, no password | One-off conversion with some risk (binary fields, FK ordering, the tiny 3-user DB makes it easy to verify though); needs a VM rehearsal; `dumpdata` must run on Arch's venv (Django 4.2) and load into nixpkgs' Django 5 — same schema after `migrate`, but worth testing |

### B. Etebase listener

- **B1. TCP `port = 25567`**: existing `etesync_creds` `serverUrl` keeps working; Caddy → `localhost:25567`. Binds 0.0.0.0 (firewall-protected) [1].
- **B2. `unixSocket`**: no TCP exposure; Caddy can proxy to a socket. But etesync-dav would need a `serverUrl` that reaches Etebase — e.g. edit `etesync_creds` to `https://etesync.nnik.dev` (goes out through Caddy) or re-add the user in the UI. Caddy must also be in the `etebase-server` group to reach the socket.

### C. etesync-dav State

- **C1. Restore all three files**: clients keep their DAV password; no re-login. `etesync_creds` must be handled as a secret in Backup (unencrypted session) [12].
- **C2. Start fresh**: restore nothing; re-add the user via the web UI (needs the Etebase password) and update the DAV password in every client. Simpler, but touches clients.

### D. etesync-dav admin UI exposure via Caddy

- **D1. Mirror today**: `header_up Host localhost:37358` on `dav.nnik.dev` → admin UI reachable from the internet (behind etesync-dav's own login) as today.
- **D2. Leave Caddy's default Host**: DAV works publicly, `/.web` admin UI is refused remotely (Flask `TRUSTED_HOSTS`) and only reachable via `ssh -L 37358:localhost:37358 optiplex`. More secure, slightly less convenient.

### E. Package version

- Use nixpkgs as-is (etebase-server 0.14.2 on Django 5, etesync-dav 0.35.1), or overlay/override to upstream HEAD (etebase `6ac5412`) / etesync-dav 0.36.0 for its Radicale and CPU fixes [10].

## Open questions

1. Postgres (A2) or keep SQLite (A1) for Etebase? Ticket 10 (database migration) owns the general approach; this is a 2.6 MB / 3-user DB.
2. Should `media_root` (11 MB) live under `/var/lib/etebase-server` on the System disk (default) or on the Data disk? Size suggests the System disk is fine.
3. Who are the 3 Etebase users (user_1, user_4, …) and are they all still active — any accounts to drop?
4. Is the etesync-dav admin UI meant to be internet-reachable (D1 vs D2)? Is `dav.nnik.dev` needed publicly at all, or LAN/VPN only, given the scanner traffic?
5. Does the Flask `TRUSTED_HOSTS` check also reject `Host: localhost:37358` with the port in Werkzeug's version shipped in nixpkgs? (Werkzeug strips the port before comparing [27], so it should pass; confirm in the VM test.)
6. Does etesync-dav 0.35.1's nixpkgs build open the 0.34.0 binary's `etebase_data.db` cleanly, or should the cache simply be dropped (it is rebuildable)?
7. Any Android/iOS EteSync clients pointing at `etesync.nnik.dev` that need checking after Cutover?
